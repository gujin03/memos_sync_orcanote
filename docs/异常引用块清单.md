## 四、根因

1. Orca 1.x 的引用是**容器块** `_repr = {"type":"quote2"}`：自身 `content` 必须为空，正文放在唯一子块里。
2. 这 19 个块的 `_repr` 是 `{"type":"text"}`，`content` 里存的是带字面 `>` 的文本片段 → 渲染成普通段落（截图里那个小圆点只是列表缩进/项目符号的视觉表现，块本身是 text）。
3. 来源是老库导入（Farbox/Logseq → Orca 迁移链）：迁移脚本只搬运了 `> ` 字面文本，没有转换块类型。
4. **与 memos 同步插件无关**：插件现已按「`^>\s?` 识别 → 建空 quote2 容器 → 正文作 text 子块」写入，149 个 quote2 结构全部规范。

## 五、修复方案

⚠️ 前置事实：Orca 的 163 个编辑器命令里**没有「就地改块类型」的命令**（只有 `batchInsertReprs` / `batchInsertHTML` 这类插入命令）。因此修复必然涉及「新建 quote2 + 删除旧块」，块 ID 会变化。

| 方案 | 做法 | 优点 | 风险/缺点 |
|---|---|---|---|
| **A. MCP 重建（推荐）** | 对每个块：`batchInsertReprs` 插入 `{type:"quote2", children:[{text}]}` → `delete_blocks` 旧块；`18308/18312` 先用 `move_blocks` 把 2 个子块迁到新引用下 | 走 Orca 官方 API，结构一定正确；可脚本化、可回滚（有备份） | 块 ID 变化 → 若有其它块引用这 19 个 ID 会断链（需先查 `BlockRef` 确认，预期为 0）；19 块 ≈ 40+ 次调用 |
| **B. 手工改** | Orca 界面里逐块选中 → 转为引用 | 零风险、不用脚本 | 19 个手工操作，重复劳动 |
| **C. 直接写 SQLite** | `UPDATE BlockProperty SET value='{"type":"quote2"}'` | 看起来最省事 | ❌ **不可行**：quote2 是容器块，只改 `_repr` 会重现「空引用 + 引述 占位符」；且 Orca 运行中锁库、内存态会覆盖，FTS 需重建 |

**已核查断链风险（结论：无风险）**

| 核查项 | 结果 |
|---|---|
| `BlockRef` 中这 19 个 ID 作为被引用目标（`t`） | **0 条** |
| 这 19 个 ID 自身发出的引用（`f`） | 0 条 |
| `BlockAlias` 命中 | 0 条 |

→ 直接重建删除**不会造成任何断链或别名丢失**，方案 A 可安全执行。

**建议走 A**，执行前只需整库备份（`cp sample.db* /tmp/...` 或 `myob-snap`）。
