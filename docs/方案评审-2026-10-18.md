## 1. 方案的整体思路与目标（复述与确认）

**一句话目标**：把插件从「能拉下来」提升到「**改得动、错得明、跑得快、渲染得像原生**」。

四层递进的结构是成立的：

| 层 | 要解决的问题 | 判据 |
|---|---|---|
| M1 数据正确性 | Memos 编辑不回写、失败被吞后静默丢数据、全量同步留下孤儿块 | 数据是否**只多不少不重** |
| M2 健壮性 | 出问题能不能定位（token 错 / filter 错 / 网络错）、异常数据会不会崩 | 能否**自证失败** |
| M3 工程化 | 构建兼容、同步耗时、类型收敛 | 可维护性 |
| M4 渲染保真 | 从「手工硬编码 `quote2`」升级到「Markdown 全量交给 Orca 自身解析」 | 输出是否接近原生编辑产物 |

**评价**：这个分层和「A 先保底、B 再彻底」的演进路线是对的——方案 A 已上线并验证可用，用它兜住引用这一最痛的点，再把列表/粗体/链接/代码交给 B。**不需要推翻，只需要修正事实、补齐遗漏。**

## 2. 逐项评估

### ① 增量同步「只增不改」— 判断：**方向保留，实现需重写（P0）**

| 维度 | 评估 |
|---|---|
| 合理 | 问题诊断准确，确实是数据正确性硬伤 |
| 不完整 | **v1 只更新标题+标签、正文标 TODO —— 这仍然是数据丢失**：一旦 `lastSyncTime` 推进，Memos 里改的正文就**永远**同步不进来了（下次增量不会再拉到这条）。而全量同步虽然能纠正，但会重建全部块、代价大 |
| 风险 | ①「标题块 = `children` 里非链接块」的定位规则太脆。链接块是最后插入的，靠"排除法"拿标题，一旦插入顺序变化就会拿错 |

**具体修订**：
1. **API 更正（P0）**：`core.editor.setContent` / `core.editor.setBlock` **不存在**。可用的同类命令（已核对 163 个注册命令）：
   - `core.editor.setBlocksContent`（✔ 存在）
   - `core.editor.setProperties`（✔，源码已用）
   - `core.editor.insertTag`（✔，源码已用）
   - `core.editor.removeTag`（✔；**`deleteTag` 不存在**）
   ```ts
   // setBlocksContent 注册体：([panelId, refBlock?, cursor], blocks, flag?)
   await orca.commands.invokeEditorCommand(
     "core.editor.setBlocksContent", null,
     [{ id: titleId, content: [{ t: "t", v: newTitle }] }],
   )
   ```
2. **正文更新不要留 TODO**：今天的实测已证明「删子块 + 重建」是可行且安全的（我们用它重建了 42 个块，`BlockRef`/`BlockAlias` 引用为 0、镜像块跟随父级自动更新）。建议把 `syncMemo` 的第 3 层写入抽成 `writeBody(titleBlock, paragraphs)` 纯函数，更新时先 `deleteBlocks(第3层子块)` 再调用同一个 `writeBody` ——**全量/增量/更新三条路径共用一份写入逻辑**。
3. **标题块定位写死规则**：给标题块打一个私有属性（如 `{name:"_memoTitle", value:true}`），查重 Map 的 value 存 `{rootId, titleId}`；不要依赖 children 顺序排除法。
4. 保留「根块 ID 属性不变」，这条是对的。

### ② 部分失败「假装成功」— 判断：**保留，补充 3 处遗漏（P1）**

- 合理：诊断与"不推进 `lastSyncTime`"的处理正确。
- **遗漏 1**：`syncMemo` 里还有两条**静默 return** —— L385 `if (!noteBlock) return`、L410 `if (!titleId) return`。它们既不抛错也不返回 false，会被当成成功。
- **遗漏 2**：`syncedCount++`（L242）在失败时也自增 → 进度数字虚高。
- **遗漏 3**：失败后"下次重跑补回"有个前提——**必须能重新拉到**。若失败原因是单条数据格式异常（不是网络），那么重跑会永远失败、永远不推进 `lastSyncTime` → **增量同步被永久卡死**。需要"连续失败 N 轮后放弃并提示"或"只把水位推进到最早失败那条之前"。
- **修订**：① 三条 return 统一改为 `return false`；② 进度只在成功时 +1；③ `lastSyncTime` 改为"推进到本轮成功项的最大 `updated_ts`"而非 `Date.now()`（顺带解决本地时钟漂移）。

### ③ 全量删除异常吞掉 + 上限硬编码 — 判断：**问题保留，改法重写（P0）**

- 合理：失败静默 → 孤儿块，判断正确。
- **P0 错误**：文档写「将单次 `query` 改为翻页循环（while `nextPageToken`）」。但 `orca.invokeBackend("query", …)` 返回 `DbId[]`（源码 L193 `as DbId[]`），**不存在 `nextPageToken`** —— 这是把 Memos HTTP 分页（确实有 `nextPageToken`）和 Orca 后端查询混淆了。
- **修订**：改为 ①实测后端 `query` 是否接受 `page/pageSize` 分页并返回总数；②若不分页，则去掉 `100000` 硬编码前先探明真实上限；③**无论如何都要把删除范围收窄**（见 ⑰）。

### ④ memoId 提取脆弱 — 判断：**保留，可直接落地（P2）**

改法正确（`name?.split("/").pop()`）。补充一点：`split("/").pop()` 对 `memos/abc` 得到 `abc` ✔，但若以后 Memos 改成 `memos/uid/xxx` 就会拿到 `xxx`。建议用 `/^memos\/(.+)$/` 捕获并断言。

### ⑤ xhr 无超时/错误不分类 — 判断：**保留，补充 2 点（P2）**

- 合理：401/400 分类提示很有价值。
- 补充 1：`xhr.onerror` 里读 `xhr.responseText` 在**网络错误**时通常是空串，提示会变成「Network error. Response: 」，建议补 `xhr.status === 0` 判定 + 提示"检查地址/代理/证书"。
- 补充 2：没有 **429 限流/重试**。Memos 自建实例一般不会限流，但批量拉取 + 失败重跑的场景建议加一档退避重试（如 3 次、指数退避）。

### ⑥ 去重键用 `b.text` 兜底 — 判断：**保留，但代码是半成品（P2）**

- 合理：文本兜底确实会误判。
- **问题**：伪代码里 `noIdBlocks.push(b)` 的 `noIdBlocks` **从未定义**，"后续人工/模糊处理"也没有落地路径 → 直接照抄会编译不过。
- **修订**：不要引入新机制。改为「无 ID 属性的块 → 跳过查重表 + `console.warn` + 计数上报」，把"人工处理"降级为日志即可。

### ⑦ 单条错误静默 — 判断：**并入 ②，行号需改（P2）**

`L455–457` 已漂移为 **L515–517**。

### ⑧ vite 配置对齐模板 — 判断：**保留，但定级错误 + 诊断要改写（P1）**

**实测证据（新）**：当前 `dist/index.js` 开头是
```js
var jsxRuntime = { exports: {} };
const _global_React = React;
var reactJsxRuntime_development = {};
... /** @license React  react-jsx-runtime.development.js */
```
即：`react` 被 external 成全局，但 **`react/jsx-runtime` 的 development 版被打进了产物**。原因是 `tsconfig.json` 的 `"jsx": "react-jsx"`（automatic runtime）+ `rollupOptions.external` 只写了 `"react"`，没写 `"react/jsx-runtime"`。

所以这不是文档里说的「当前能跑，属兼容保险」——**是已经发生的双运行时 + 生产包夹带 development 版**。定级应从 🟢 提到 🟡。

**修订（三选一，推荐 a）**：
- **a. 强制 classic**：SWC 设 `jsx: "transform-classic"`（同时把 `tsconfig` 的 `"jsx"` 改为 `"react"` 保持一致），产物用全局 `React.createElement`，与模板一致。
- b. 补 external：`external` 与 `externalGlobals` 都加 `"react/jsx-runtime": "ReactJSXRuntime"`（需确认 Orca 是否暴露该全局，风险较高，**不推荐**）。
- c. 不动：功能无 bug，仅体积与 dev 检查开销（可接受但应知情）。
- 另：文档说「补 `react-dom` external」——本插件**源码完全没有 import react-dom**（`grep` 仅命中 `orca.d.ts` 注释），加了收益为零，可从改动清单删除以免分散注意力。

### ⑨ 串行 insert 性能 — 判断：**方向需改（P1）**

- 问题真实：每条 memo 至少 5 次 `invokeEditorCommand`。
- **方向错误**：文档建议「每批 10 条 `Promise.all`」。今天的实证表明 Orca 的块顺序完全依赖 `left` 指针链（我们正是用 `left` 链校验顺序的），**并发插入会互相覆盖 `left`，导致顺序错乱**。这不是"需实测是否允许并发"，而是**结构上就不该并发写块**。
- **修订**：① 放弃并发，改为**批量 API**（`core.editor.batchInsertReprs` 一次插入整棵 repr 树，含 quote2 + 子块），把「每条 5 次调用」压到「1 次」；② 把 5 次调用里的 `setProperties` + `insertTag` 与 insertBlock 合并顺序，减少中间态；③ 验收标准从"耗时下降"改为"调用次数下降 + 顺序不变"。

### ⑩ TS 类型收敛 — 判断：**保留（P2）**

改法正确。补充：`tsconfig` 已开 `strict: true`，`noImplicitAny` 生效中，所以验收标准里"未开 noImplicitAny"这句已过时，应改为「消除显式 `any`（`xhrRequest` 返回、`null as any`）」。

### ⑪-A 引用渲染（已实施）— 判断：**保留，补 2 条保真修订（P2）**

已实施并验证，文档对 `quote2` 容器机制的修正正确。两点补充：

1. **多行引用应拆成多个子块**：当前 `lines.join("\n")` 把连续引用行压成**一个** text 子块。而今天的 MCP 实测（`"> a\n> b"` → **一个 quote2 + 两个 text 子块**）证明 Orca 原生形态是**每段一个子块**。建议 `for (const line of lines) insertBlock(quote, "lastChild", [line])`。
2. **行内 `>` 未处理**（见 ⑯）。

### ⑪-B 方案 B / M4 — 判断：**风险应降级，前置条件需更新（P2）**

文档写「调用签名需实测、`convertHTMLToReprs` 是否支持 BLOCKQUOTE 待验证」。**今天的实测已把大部分不确定性打掉了**：

- 我们通过 MCP 的 `insert_markdown`（其底层就是 `core.editor.batchInsertHTML`）共插入 **42 个块**，全部 `success`：
  - `"> 正文"` → 一个 `quote2` 容器 + 一个 text 子块 ✔
  - `"> 1、…\n> 2、…"` → **一个 quote2 + 两个 text 子块** ✔（多段引用天然正确）
  - `"## 标题"` → `heading` level 2 ✔
  - `"正文"` → text ✔
- **另需修正一个误解**：`core.editor.insertQuote` 是「插入一个新的空引用块并把光标放进去」，**不会把已有内容搬进引用**（空块分支只改 `_repr`，非空块分支是 `insertBlock(after)` + 插一个空 firstChild）。所以别指望用它替代方案 A 的"容器+子块"。

**修订**：M4 的前置条件从「签名 + 转换器能力」两项，收敛为只剩：
1. **`batchInsertHTML` 自己的参数顺序**（`[panelId, _, refBlock]` + `position` + `html`）——MCP 已封装好，插件直接调仍需实测；
2. **Memos 语法预处理**（`#tag` 会被当 H1、`[[wikilink]]`、`- [ ]`）；
3. 新增：**容器性必须由 Orca 转换器决定，不能自己映射**。今天的类型普查证明"容器性按类型而异"：

| 块类型 | 总数 | content 非空 | 有子块 | 结论 |
|---|---|---|---|---|
| `quote2` | 193 | **0** | **193** | 纯容器（100% 一致） |
| `table2` | 32 | **0** | **32** | 纯容器 |
| `journal` | 1269 | 0 | 1053 | 容器 |
| `ul` | 764 | **764** | 199 | **内联**（不是容器） |
| `heading` / `code` / `ol` | 625 / 239 / 63 | 全部非空 | — | 内联 |

→ 手工映射时若把 `ul` 也当容器处理就会翻车；这正是不该自己映射、应交给 `convertHTMLToReprs` 的硬理由。

## 3. 文档未覆盖的真实缺陷（建议新增条目）

### ⑫ 可见性「全不选」= 同步全部（P1，逻辑与 UI 语义相反）
源码 L290–296：
```ts
if (visibilityFilter?.length > 0 && visibilityFilter.length < 3) { ... }
```
用户把三项**全部取消** → 配置为空数组 → 条件为 false → **不加任何 visibility 过滤** → 同步**所有**可见性。而 UI 文案是「Unchecked items will be excluded」。
**修订**：`visibilityFilter.length === 0` 时 `notify("warn", "未选择任何可见性，已取消同步")` 并 return。

### ⑬ 无并发锁，连点即重复（P1）
`syncMemos` 无重入保护，工具栏图标点击会直接 `invokeCommand`。两次并发 → 同一 memo 被插两遍（查重表是启动时快照，第二次看不到第一次的写入）。
**修订**：模块级 `let syncing = false`，进入即置位、`finally` 复位；置位时 `notify("warn","同步进行中")` 并 return。

### ⑭ Memos 删除不回收（P1，反向同步缺失）
增量同步只做「拉取 → 查重 → 新建」，**永不清理由 Memos 删除的 memo**。
**修订**（注意实现细节）：不能用「本次拉取集合」做差集——增量只拉 `updated_ts >= lastSync`，集合本身不完整。可行方案：
1. 增加「清理」模式：全量拉 memo id（仅 id，`pageSize` 小、按页滚动）→ 与 `allExistingIds` 里带 ID 属性的块做差集 → 列出待删清单，**先 dry-run 通知用户确认**；
2. 或给根块加 `_memoSyncedAt` 时间戳，超过 N 天未出现的块标灰（保守方案，不自动删）。
建议先做 1 的 dry-run，不做自动删除。

### ⑮ 多行引用合并成单子块（P2）
同 ⑪-A 修订 1。

### ⑯ 行内 `>` 引用未处理（P2）
Memos 里常出现「他说： > 这句话」这种**行内**引用（原文另起一行，被 `\n` 分割前的软换行压平）。插件按 `^>` 判定块首引用，行内的一律当普通文本，会残留字面 `>`。
> 实证：本次在库里就清出了 **23 个**这类块（5 + 18），全部是「…观点： > 引文」形态。
**修订**：在段落内部再做一次切分——`/([：。；，、])\s*>\s*/` 命中则「前半段 → text 块，后半段 → quote 块」，与 ⑪-A 复用同一个 `writeQuote()`。

### ⑰ 全量删除范围可能误伤（P1）
删除依据是 `{kind:1, conditions:[{kind:4, name:noteTag}]}`，即「带 `#Memos Note` 标签的所有块」。若用户手工给别的块打了同名标签，全量同步会连它一起删。
**修订**：删除前过滤「**同时具备 ID 属性**」的根块（插件产物特征），并在通知里报出「将删除 N 块（已过滤 M 块非插件块）」。

| **M3 工程化** | ⑧（提到 🟡，二选一修法）、⑨（改批量而非并发）、⑩ | 方向修订 |
| **M4 渲染保真** | ⑪-B + ⑮ 多段引用 + ⑯ 行内 `>` | 风险降级、范围明确 |

**顺序理由**：M0 是"不先做就会白做"；⑫⑬ 改动极小但直接决定"会不会重复/越权同步"，放在 M1 之后立刻做；M4 放到最后，因为它会替换整条内容写入路径，必须等 M1 的 `writeBody()` 抽取完成，才能只换"渲染层"而不动"同步逻辑层"。

## 7. 一句话总评

**方案的"分层与方向"不用改，"事实与遗漏"必须改。** 最危险的不是 M1 里的三个显式条目（那些用户已知），而是三件文档完全没提的事：**可见性全选反成全同步、连点即重复、Memos 删了 Orca 不删**——这三条都属于"静默发生、事后难查"的问题，与插件一贯的"外部依赖静默腐烂"是同一类病。
