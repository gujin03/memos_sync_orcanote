## 3. 🔴 M1 数据正确性

### ① 增量同步「只增不改」→ 改为「更新」（含正文）

- **位置**：查重 L359–361；查重表构建 L215–229；标题 L403–410；正文 L432–499
- **现状**
  ```ts
  if (existingBlocks.has(memoId)) { return }   // L359-361
  ```
- **问题**：Memos 端编辑后 `updated_ts` 命中被拉回，但因已存在而跳过 → **编辑永远进不来**。
- **v1.0 的"v1 只更新标题+标签、正文标 TODO"不可接受**：一旦水位推进，正文编辑就**永久丢失**（下次增量不会再拉到这条）。必须完整更新。
- **目标行为**：命中 → 原地更新（标题文本 + 标签差分 + 正文重建），根块 ID 与 ID 属性不变。

**改动要点**

1. **API 更正**（M0 结论）：
   ```ts
   // 改标题文本（正确 API）
   await orca.commands.invokeEditorCommand(
     "core.editor.setBlocksContent", null,
     [{ id: titleId, content: [{ t: "t", v: newTitle }] }],
   )
   // 删标签（正确 API；签名据注册体推断，落地前调用一次确认）
   await orca.commands.invokeEditorCommand(
     "core.editor.removeTag", null, titleId, tagName,
   )
   ```
2. **查重表 value 结构化**：`Map<string, { rootId: DbId; titleId: DbId }>`。
3. **标题块定位不靠"children 排除法"**：给标题块打私有属性 `{ name: "_memoTitle", value: true }`，构建查重表时按属性识别（O(1)、不受插入顺序影响）。
4. **抽出 `writeBody()` 纯函数**（关键重构）：把 L432–499 的正文写入逻辑抽出，三条路径共用：
   - 新建：`writeBody(titleBlock, paragraphs)`（当前无子块）
   - 更新：`deleteBlocks(titleBlock.children)` → `writeBody(...)`
   - 全量：删旧块后重建（天然走新建路径）
   ```ts
   async function writeBody(titleBlock: Block, paras: string[]) {
     const old = titleBlock.children ?? []
     if (old.length) {
       await orca.commands.invokeEditorCommand("core.editor.deleteBlocks", null, old)
     }
     // …原 L432–499 的循环（引用识别 → quote2 容器 + 子块）
   }
   ```
5. 标签差分：`目标 = memo.tags`，`现有 = 标题块 _tags 属性`；差集分别 `insertTag` / `removeTag`。
- **影响**：增量可回写；全量路径不变；块 ID（正文层）会变化——已核查 `BlockRef`/`BlockAlias` 对插件块引用为 0，mirror 镜像的是父级子树会跟随，**安全**。
- **验收**
  - Memos 改标题 → 增量后 Orca 标题更新。
  - Memos 增删标签 → Orca 标题块标签同步。
  - **Memos 只改正文 → 增量后 Orca 正文块内容更新**（v1.0 缺失的核心项）。
  - 更新不产生重复块（同一父块下子块数量与 Memos 段落数一致）。

### ② 部分失败被「假装成功」

- **位置**：水位 L250；`syncMemo` catch L515–517；主循环 L240–247
- **问题（比 v1.0 记录的多 3 处）**
  1. catch 静默吞掉，不计数；
  2. **另有两条静默 return**：L385 `if (!noteBlock) return`、L410 `if (!titleId) return` —— 既不抛错也不返回 false，会被当成功；
  3. `syncedCount++`（L242）失败时也自增 → 进度虚高。
- **补充风险（v1.0 未提）**：若失败是**单条数据格式异常**（非网络），"不推进水位"会导致重跑永远失败 → **增量同步永久卡死**。
- **目标行为**：累计失败数；有失败则水位**只推进到本轮成功项的最大 `updated_ts`**；连续失败 N 轮则告警并允许跳过。
- **改动要点**
  ```ts
  // 1) 三条 return 统一改为 return false
  // 2) 主循环
  for (const memo of memosInDate) {
    const ok = await syncMemo(...)
    if (ok) { syncedCount++; maxOkUpdatedTs = Math.max(maxOkUpdatedTs, tsOf(memo)) }
    else failedCount++
  }
  // 3) 水位：用服务器时间而非本地时钟（顺带解决时钟漂移）
  if (failedCount === 0) await setData("lastSyncTime", maxOkUpdatedTs)
  else if (maxOkUpdatedTs) await setData("lastSyncTime", maxOkUpdatedTs) // 只推进到最早失败点之前
  // 4) 通知区分计数
  orca.notify(failedCount ? "warn" : "success", `成功 ${syncedCount} 条，失败 ${failedCount} 条`)
  ```
- **验收**
  - 人为制造 1 条失败 → 提示含失败数；水位不越过失败项（下次能重拉）。
  - 下次重跑 → 失败条补回，成功项不重复。
  - 同一条连续失败 3 轮 → 有明确告警（不死锁）。

### ③ 全量删除异常吞掉 + 上限硬编码

- **位置**：查询 L190–193（`pageSize: 100000`）；删除循环 L201–209（catch L206–208）
- **问题**：删除失败仅 `warn` 继续 → 旧块残留 + 新建新块 = **孤儿/重复**；10 万上限会静默截断。
- **v1.0 改法不可实现**：写的是"改翻页循环 `while nextPageToken`"，但 `orca.invokeBackend("query", …)` 返回 `DbId[]`，**没有 pageToken**（那是 Memos HTTP 接口的特性）。
- **目标行为**：取全 + 失败即中断 + 范围收窄（见 ⑰）。
- **改动要点**
  1. **先实测后端 `query` 的分页语义**（是否支持 `page`/`pageSize`、是否返回总数）。若支持：
     ```ts
     const PAGE = 1000
     let page = 1; const all: DbId[] = []
     while (true) {
       const ids = await orca.invokeBackend("query", { q, pageSize: PAGE, page }) as DbId[]
       if (!ids?.length) break
       all.push(...ids)
       if (ids.length < PAGE) break
       page++
     }
     ```
     若不支持：保留单次查询，但把上限提高并把"命中数 == 上限"作为**可疑告警**（`notify("warn", "查询可能被截断")`），不再静默。
  2. 删除失败 → 计数 + `notify("warn")` + **中断后续批次**（避免半删），并建议用户重试；不要"失败也继续"。
  3. 删除完成后断言：`删除数 == 计划数`，否则告警。
- **影响**：仅全量路径。
- **验收**
  - 数据量超上限时**不静默截断**（要么取全，要么明确告警）。
  - 模拟删除失败 → 中断 + 提示失败数，不留半删状态。

### ⑰ 全量删除范围可能误伤用户块

- **位置**：L190–193 的查询 `{ q: { kind: 1, conditions: [{ kind: 4, name: noteTag }] } }`
- **问题**：匹配依据是「带 `#Memos Note` 标签的所有块」。用户若手工给别的块打同名标签，**全量同步会连它一起删**。
- **目标行为**：只删插件产物（**同时具备 `ID` 属性**的根块）。
- **改动要点**
  ```ts
  const blocksData = await orca.invokeBackend("get-blocks", allExistingIds) as Block[]
  const pluginRootIds = (blocksData ?? [])
    .filter(b => b?.properties?.some(p => p.name === "ID"))
    .map(b => b.id)
  const skipped = allExistingIds.length - pluginRootIds.length
  orca.notify("info", `将删除 ${pluginRootIds.length} 块（已跳过 ${skipped} 块非插件块）`)
  ```
- **验收**：手工造一个带同名标签、无 `ID` 属性的块 → 全量同步后它**仍存在**，且通知里报出跳过数。

## 4. 🟠 M1.5 运行时护栏

### ⑫ 可见性「全不选」= 同步全部（与 UI 语义相反）

- **位置**：L290–296
- **现状**
  ```ts
  if (visibilityFilter?.length > 0 && visibilityFilter.length < 3) { …加过滤… }
  ```
- **问题**：三项全部取消 → `[]` → 条件为 false → **不加任何过滤 → 同步所有可见性**。而 UI 文案是「Unchecked items will be excluded」。这是**隐私/范围失控**。
- **目标行为**：空数组 = 不同步，并明确提示。
- **改动要点**
  ```ts
  if (visibilityFilter?.length === 0) {
    orca.notify("warn", t("未选择任何可见性，已取消同步"))
    return
  }
  ```
- **验收**：三项全不选 → 提示 + 不同步（库中无新增/无删除）。

### ⑬ 无并发锁，连点即重复

- **位置**：`syncMemos` 入口 L137
- **问题**：工具栏图标点击直接 `invokeCommand`。两次并发 → 查重表是启动快照，第二次看不到第一次写入 → **同一 memo 插两遍**。
- **改动要点**
  ```ts
  let syncing = false
  async function syncMemos(fullSync: boolean) {
    if (syncing) { orca.notify("warn", t("同步进行中，请稍候")); return }
    syncing = true
    try { …原逻辑… } finally { syncing = false }
  }
  ```
- **验收**：连点两次 → 第二次被拒绝；库中对应 memo 只有一份。

## 5. 🟡 M2 健壮性

### ④ memoId 提取脆弱

- **位置**：L356 `memo.name.replace("memos/", "")`
- **问题**：`name` 为空或格式变化（如将来 `memos/uid/xxx`）会得到错误 ID，污染查重/ID 属性。
- **改动要点**
  ```ts
  const memoId = /^memos\/(.+)$/.exec(memo.name ?? "")?.[1]?.trim() ?? ""
  if (!memoId) { console.warn("MEMOS SYNC: bad memo.name", memo.name); return false }
  ```
- **验收**：`name` 为空 / `memos/` / 异常格式 → 安全跳过并计入失败，不写库。

### ⑤ xhr 无超时 + 错误不分类

- **位置**：L321–346
- **问题**：无 `timeout`；401/400/网络错同一文案；`xhr.status === 0` 时 `responseText` 为空，提示退化为 `Network error. Response: `。
- **改动要点**
  ```ts
  xhr.timeout = 30000
  xhr.ontimeout = () => reject(new Error("请求超时：请检查 memos 服务是否可达"))
  // 分类：401 → "API Token 无效或已过期"；403 → "无权限"
  //       400 → "请求参数错误（filter 语法）"
  //       status===0 → "网络不可达：检查地址/代理/证书"
  //       429 → 退避重试（最多 3 次，指数退避）
  ```
- **验收**：错误 token → 提示「API Token 无效或已过期」；地址填错 → 提示网络不可达（不是空 Response）。

### ⑥ 去重键用 `b.text` 兜底

- **位置**：L221–226
- **问题**：无 `ID` 属性的块（手工/旧版导入）用正文当键 → 误判；同 memo 多份只留首个（查重够用，但重复块不会被清理）。
- **v1.0 的伪代码不可用**：其中 `noIdBlocks.push(b)` 的 `noIdBlocks` **从未定义**，"后续人工/模糊处理"也无落地路径 → 照抄编译不过。
- **改动要点**（不引入新机制，降级为留痕）
  ```ts
  const idProp = b.properties?.find(p => p.name === "ID")
  if (!idProp?.value) { console.warn("MEMOS SYNC: block without ID prop", b.id); continue }
  const memoId = String(idProp.value)
  if (!existingBlocks.has(memoId)) existingBlocks.set(memoId, { rootId: b.id, titleId })
  ```
- **验收**：库中存在无 ID 属性的旧块 → 不被误判为已同步；日志有留痕。

### ⑦ 单条错误静默

- **位置**：L515–517（**行号已从 v1.0 的 L455–457 漂移**）
- **说明**：不单独成块，随 ② 落地（`return false` + 主循环统计 + `notify`）。

### ⑭ Memos 删除的 memo 永不回收（反向同步缺失）

- **位置**：无（**v1.0 完全缺失**）
- **问题**：增量只做「拉取 → 查重 → 新建」，Memos 里删掉的 memo 在 Orca 永远残留。
- **实现注意**：**不能用「本次拉取集合」做差集**——增量只拉 `updated_ts >= 水位` 的条目，集合本身不完整，会误删大量正常块。
- **改动要点（保守方案，推荐先做 dry-run）**
  1. 新增「清理」入口（或全量同步前置步骤）：**全量拉 memo id**（只要 id，`pageSize` 小、按页滚动）→ 得到全集 `B`；
  2. 取库中带 `ID` 属性的根块 `A`；
  3. `A - B` = 已删除 → **只打印/通知清单，不自动删**；
  4. 用户在 Orca 里确认后，再走一次删除（或提供设置项 `autoCleanDeleted=false`）。
- **验收**
  - dry-run 清单与实际差集一致，确认前**库无变化**。
  - 增量同步（非清理模式）不会误删任何块。

## 6. 🟡 M3 工程化

### ⑧ 生产包夹带 `react-jsx-runtime.development`（原定级过低，🟢→🟡）

- **位置**：`vite.config.ts`（`external: ["react","valtio"]`）+ `tsconfig.json`（`"jsx": "react-jsx"`）
- **实测证据**：`dist/index.js` 开头即为
  ```js
  var jsxRuntime = { exports: {} };
  const _global_React = React;
  var reactJsxRuntime_development = {};
  /** @license React  react-jsx-runtime.development.js */
  ```
  即 `react` 走 external 全局，而 **`react/jsx-runtime` 的 development 版被打进产物**（因为 automatic runtime 会 import `react/jsx-runtime`，但 `external` 只写了 `"react"`）。
- **所以这不是"能跑就行"的兼容保险，是已经发生的缺陷**：双运行时 + 生产包带 dev 检查开销。
- **改动要点（三选一，推荐 a）**
  - **a. 强制 classic**：SWC 设 `jsx: "transform-classic"`，同时 `tsconfig` 的 `"jsx"` 改为 `"react"`（保持一致性）→ 产物用全局 `React.createElement`。
  - b. 补 external：`external` + `externalGlobals` 都加 `"react/jsx-runtime"`（**需确认 Orca 暴露该全局，风险高，不推荐**）。
  - c. 维持现状（知情接受，仅体积/开销代价）。
  - ⚠️ 删掉 v1.0 的"补 `react-dom` external"——源码未 import react-dom，收益为零。
  - 可选：同步最新 `orca.d.ts`（模板 6124 行 vs 现有 5484 行，含 `orca.ai`）。
- **验收**：`grep -c "jsx-runtime" dist/index.js` = **0**（走 a 时）；插件加载与同步无回归。

### ⑨ 串行 insert 性能 → 改「批量」，**不要并发**

- **位置**：主循环 L240–247；正文循环 L432–499
- **问题**：每条 memo ≥5 次 `invokeEditorCommand`（根块、setProperties、insertTag、标题、正文 N 次、链接）。
- **v1.0 的"每批 10 条 `Promise.all`"方向错误**：Orca 块顺序完全依赖 `left` 指针链（本项目正是用 `left` 链校验顺序的，数值排序会误判），**并发插入会互相覆盖 `left`** → 顺序错乱。这不是"需实测"，而是**结构上不该并发写块**。
- **改动要点**
  1. 用 `core.editor.batchInsertReprs` 一次插入整棵 repr 树（根块 + 标题 + 引用容器/子块 + 链接），把"每条 5+ 次调用"压到"1–2 次"；

  3. 如需进一步提速，只在"拉取/解析"阶段并行（纯计算），**写块阶段严格串行**。
- **验收**：单条 memo 调用次数 ≤2；同一父块下子块顺序与 Memos 原文一致（按 `left` 链核对）；500 条耗时下降。

## 7. 🟢 M4 渲染保真

### ⑪-A 引用渲染（**已实施上线**，`fc71971` + `212def1`）

**现状（L432–499）**：识别 `^>\s?` → 建**空 `quote2` 容器** → 正文作为 **text 子块**插入。

> ⛔ **必须记住的坑（两次实测）**
> 1. 第一版把正文当**内联 content** 传给 quote2 → 引用块**显示为空**、只有「引述」占位符。
> 2. **根本原因：`quote2` 是容器块，只渲染子块，不渲染内联 content。** 正确写法＝空容器（content 传 `null`）+ text 子块。
> 3. 库内实证：149 个 quote2 中 125 个 `content=NULL`（其中 112 个恰有 1 个 text 子块＝原生形态）；24 个 `content` 非空且子块数=0，正是第一版 bug 的产物（已全量同步修正）。
> 4. ⚠️ 别想用 `core.editor.insertQuote` 简化：它是「插入一个新的空引用块并放光标」，**不会搬运已有内容**。

**A 验收**
- 全量同步后，原 `> ` 段落 → `quote2` 容器（`content=NULL`）+ 1 个 text 子块，子块文本不含 `> `。
- 不出现「引述」占位符。
- 非引用段落仍为 text 块。

### ⑮ 多行引用应拆成多个子块（保真修订）

- **位置**：L449 `text = lines.join("\n")`
- **问题**：连续引用行被压成**一个** text 子块（内含 `\n`）。而 Orca 原生形态是**每段一个子块**——已用 MCP `insert_markdown("> a\n> b")` 实测：产出**一个 quote2 + 两个 text 子块**。
- **改动要点**
  ```ts
  // 由 join("\n") 改为逐行插子块
  for (const line of lines) {
    if (!line.trim()) continue
    await orca.commands.invokeEditorCommand(
      "core.editor.insertBlock", null, quoteBlock, "lastChild",
      [{ t: "t", v: line }], { type: "text" },
    )
  }
  ```
- **验收**：三行连续引用 → 一个 quote2 内含 **3 个** text 子块（不是 1 个带换行的）。

### ⑯ 行内 `>` 引用未处理（拆块）

- **位置**：L438–456（只判块首 `^>`）
- **问题**：Memos 里「他说： > 这句话」这种**行内**引用（原文另起一行、被软换行压平）一律当普通文本，残留字面 `>`。
  > 实证：本次在库里清出 **23 个**这类块（5 + 18），全部是「…观点： > 引文」形态。
- **改动要点**：段落内再切一刀，命中则「前半段 → text 块，后半段 → quote 块」，复用同一个 `writeQuote()`：
  ```ts
  const INLINE_QUOTE = /([：:。；;，,、])\s*>\s*/
  const m = INLINE_QUOTE.exec(para)
  if (m) {
    await insertTextBlock(m[1] ? para.slice(0, m.index + m[1].length) : "")
    await writeQuote(para.slice(m.index + m[0].length))
  }
  ```
- **验收**：含「…： > 引文」的 memo 同步后拆成 text + quote 两块，全文无字面 `>`。

### ⑪-B 方案 B / Markdown 全量接管（进阶段，风险已降级）

**结论**：原理与 API 均已实证，**不再是"待验证签名与能力"**，剩两项前置 + 一项架构约束。

#### 机制（asar 注册体实证）
```js
registerEditorCommand("core.editor.batchInsertHTML", async ([mr,,ur],pr,Ji,Uo)=>{
  const Da = new DOMParser().parseFromString(Uo,"text/html");
  const uu = await convertHTMLToReprs(Da.body);   // HTML → 原生块 repr
  if (uu.length===0) return null;
  …
  return { ret: await hu.viewState.editor.invokeCommand("core.editor.batchInsertReprs", ur, pr, Ji, uu) };
})
```
`convertHTMLToReprs` 是 Orca **粘贴 / HTML 导入**复用的核心转换器（asar 出现 7 次）；`BLOCKQUOTE/STRONG/CODE/PRE/UL/OL/LI/EM` 大量出现。MCP `insert_markdown` 即其封装（`ORCA_API_REFERENCE.md` L502）。

#### 已实测通过的行为（MCP `insert_markdown`，共插 42 块零失败）

|---|---|---|---|---|
| `quote2` | 193 | **0** | **193** | 纯容器 |

| `journal` | 1269 | 0 | 1053 | 容器 |
| `ul` | 764 | **764** | 199 | **内联（不是容器）** |
| `heading` / `code` / `ol` | 625 / 239 / 63 | 全部非空 | — | 内联 |

→ 手工映射若把 `ul` 也当容器处理必然翻车。**这正是必须交给 `convertHTMLToReprs` 的硬理由**。

3. **依赖与回退**：需引入 `marked`（或复用 Orca 解析）；保留方案 A 作回退开关（设置项 `renderMode: "quote-only" | "markdown"`）。

3. 在 Memos 改一条 memo 的**正文** → 再增量同步 → Orca 里该 memo 正文应更新（这是 ① 的核心验收）。
4. 连点两次同步 → 第二次应提示「同步正在进行中」。
5. 三项可见性全不选 → 应提示「未选择任何可见性，已取消同步」而非照常同步。

## 12. 调研结论：⑨ 与 ⑪-B 的硬前置（2026-10-18 22:00）

两条"进阶段"卡在同一个问题上：**Orca 的这些批量命令不是纯数据 API，而是"编辑器命令"**。

### ⑨ `core.editor.batchInsertReprs`
注册体（asar 实证）：
```js
registerEditorCommand("core.editor.batchInsertReprs", async (mr, ur, pr, Ji) => {
  let parent = null, left = null
  switch (pr) {
    case "before":     { parent = ur.parent; left = ur.left; break }
    case "after":      { parent = ur.parent; left = ur.id; break }
    case "firstChild": { parent = ur.id;     left = null; break }
    case "lastChild":  { parent = ur.id;     left = ur.children?.at(-1) ?? null; break }
  }
  const [undoArgs, blocks, ret] = await orca.invokeBackend(BatchInsertReprs, parent, left, Ji)
  for (const b of blocks) orca.state.blocks[b.id] = b
  return { ret, undoArgs }
})
```
- **position 语义已确认**，父块 / 左兄弟由它自动换算 → 调用方只需给 `(refBlock, position, reprs)`。
- **卡点**：`Ji`（reprs）的元素结构由后端 `BatchInsertReprs` 定义，**asar 里查不到**（`convertHTMLToReprs` 已改名/内联，拿不到样例）。盲写会建出错误块，且无法在无 GUI 的环境里验证。
- **解法（待做）**：在 Orca 里手动插入一条引用 + 一个列表 + 一段代码，用「复制为 JSON」或读库反推 repr 树结构，再实现批量路径。

### ⑪-B `core.editor.batchInsertHTML`
```js
registerEditorCommand("core.editor.batchInsertHTML", async ([mr,,ur], pr, Ji, Uo) => {
  const doc = new DOMParser().parseFromString(Uo, "text/html")
  const reprs = await convertHTMLToReprs(doc.body)
  if (!reprs.length) return null
  const panel = orca.nav.findViewPanel(mr, orca.state.panels)   // ← mr 必须是真实 panelId
  return { ret: await panel.viewState.editor.invokeCommand(...) }  // ← panel 为 undefined 则抛
})
```
- **卡点**：`mr`（panelId）必须是已存在的面板；插件侧若传 `null`，`findViewPanel` 返回 `undefined` 后直接解引用 → 抛错。
  MCP 的 `insert_markdown` 能工作，是因为它由 Orca 侧带上下文调用，不是插件调用。
- **待验证的解法**：从 `orca.state.panels` 取一个 panel 的 id 作为 `mr`（例如当前活动面板），或改用 `orca.state.activePanelId`（若存在）。需要一次运行时探测确认字段名。

### 结论
在拿到 `reprs` 结构 / 可用 panelId 之前，**不实现这两条**——它们的失败模式是"静默建错块"，比现在的逐块插入更危险。
当前插件（方案 A + 逐块插入）已能正确渲染引用，属于可用状态。
